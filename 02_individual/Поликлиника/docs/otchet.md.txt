# Индивидуальная работа
## Разработка базы данных предметной области «Поликлиника»

### 1. Цель работы

Целью работы является проектирование и создание реляционной базы данных для автоматизации работы поликлиники. В ходе работы необходимо выделить основные сущности предметной области, определить связи между ними, построить ER-диаграмму, выполнить нормализацию до третьей нормальной формы, создать базу данных SQLite и подготовить SQL-запросы для обработки информации.

### 2. Описание предметной области

Поликлиника — медицинское учреждение, в котором пациенты записываются на приём к врачам различных специальностей. В процессе работы необходимо хранить информацию о пациентах, врачах, кабинетах, записях на приём, диагнозах и назначениях.

Разрабатываемая база данных позволяет:
- хранить сведения о пациентах;
- хранить информацию о врачах и их специальностях;
- учитывать кабинеты поликлиники;
- регистрировать записи на приём;
- фиксировать диагнозы пациентов;
- хранить информацию о назначенных лекарствах;
- получать статистику по приёмам и врачам.

### 3. Выделение сущностей и атрибутов

В предметной области выделено 8 основных сущностей.

**1. Specialties (Специальности)**
- specialty_id — идентификатор специальности;
- name — название специальности;
- description — описание.

**2. Patients (Пациенты)**
- patient_id — идентификатор пациента;
- full_name — ФИО пациента;
- birth_date — дата рождения;
- gender — пол;
- phone — номер телефона;
- address — адрес проживания.

**3. Doctors (Врачи)**
- doctor_id — идентификатор врача;
- full_name — ФИО врача;
- specialty_id — идентификатор специальности;
- phone — номер телефона.

**4. Rooms (Кабинеты)**
- room_id — идентификатор кабинета;
- room_number — номер кабинета;
- floor — этаж.

**5. Appointments (Приёмы)**
- appointment_id — идентификатор приёма;
- patient_id — идентификатор пациента;
- doctor_id — идентификатор врача;
- room_id — идентификатор кабинета;
- appointment_datetime — дата и время приёма;
- status — статус приёма;
- notes — примечание.

**6. Diagnoses (Диагнозы)**
- diagnosis_id — идентификатор диагноза;
- icd_code — код диагноза по МКБ;
- name — название диагноза;
- description — описание.

**7. Appointment_Diagnoses (Диагнозы приёмов)**
- appointment_id — идентификатор приёма;
- diagnosis_id — идентификатор диагноза.

**8. Prescriptions (Назначения)**
- prescription_id — идентификатор назначения;
- appointment_id — идентификатор приёма;
- medication_name — название препарата;
- dosage — дозировка;
- instructions — инструкция по применению.

### 4. ER-модель и связи между сущностями

В базе данных реализованы следующие связи:

- Specialties — Doctors: один ко многим (1:M). Одна специальность может быть у нескольких врачей.
- Patients — Appointments: один ко многим (1:M). Один пациент может иметь несколько записей на приём.
- Doctors — Appointments: один ко многим (1:M). Один врач может проводить несколько приёмов.
- Rooms — Appointments: один ко многим (1:M). В одном кабинете могут проходить разные приёмы в разное время.
- Appointments — Diagnoses: многие ко многим (M:N). Один приём может иметь несколько диагнозов, а один диагноз может встречаться на разных приёмах. Для реализации используется промежуточная таблица Appointment_Diagnoses.
- Appointments — Prescriptions: один ко многим (1:M). В рамках одного приёма может быть оформлено несколько назначений.

ER-диаграмма представлена в отдельном файле er_diagram.mmd.

### 5. Нормализация базы данных

Структура базы данных приведена к третьей нормальной форме (3НФ).

**Первая нормальная форма (1НФ).**

Все атрибуты содержат атомарные значения. В таблицах отсутствуют повторяющиеся группы и массивы значений. Связь между приёмами и диагнозами вынесена в отдельную таблицу Appointment_Diagnoses.

**Вторая нормальная форма (2НФ).**

Все неключевые атрибуты полностью зависят от первичного ключа. В таблице Appointment_Diagnoses используется составной первичный ключ из appointment_id и diagnosis_id. Неключевые атрибуты в этой таблице отсутствуют.

**Третья нормальная форма (3НФ).**

Транзитивные зависимости устранены. Информация о специальностях хранится отдельно от врачей, а информация о диагнозах — отдельно от приёмов. Это позволяет избежать дублирования данных и упрощает их обновление.

### 6. Реализация базы данных в SQLite

Для создания базы данных использована СУБД SQLite и программа DB Browser for SQLite.

Создан файл базы данных polyclinic.db, содержащий 8 таблиц:
- specialties;
- patients;
- doctors;
- rooms;
- appointments;
- diagnoses;
- appointment_diagnoses;
- prescriptions.

Для обеспечения целостности данных применены первичные и внешние ключи, ограничения NOT NULL, UNIQUE и CHECK.

### 7. Заполнение базы данных

Для заполнения таблиц подготовлены CSV-файлы в кодировке UTF-8.

В базу импортированы тестовые данные:
- 4 специальности;
- 6 пациентов;
- 4 врача;
- 4 кабинета;
- 5 диагнозов;
- 8 приёмов;
- 6 связей между приёмами и диагнозами;
- 5 назначений.

Импорт данных выполнен через DB Browser for SQLite. При загрузке соблюдался порядок, учитывающий зависимости между таблицами.

### 8. SQL-запросы

Для проверки работы базы данных разработано 15 SQL-запросов.

Запросы позволяют:
1. Получить список всех пациентов.
2. Вывести врачей с их специальностями.
3. Получить расписание приёмов.
4. Подсчитать количество пациентов по полу.
5. Подсчитать количество приёмов каждого врача.
6. Получить статистику приёмов по статусам.
7. Найти пациентов с завершёнными приёмами.
8. Получить приёмы конкретного врача.
9. Вывести диагнозы по каждому приёму.
10. Получить список назначенных лекарств.
11. Найти пациентов с несколькими приёмами.
12. Найти врачей с количеством приёмов выше среднего.
13. Определить наиболее распространённый диагноз.
14. Получить приёмы за октябрь 2026 года.
15. Найти кабинеты, в которых было более одного приёма.

В запросах использованы SELECT, JOIN, LEFT JOIN, GROUP BY, ORDER BY, COUNT, HAVING, EXISTS и вложенные подзапросы.

### 9. Индексация

Для ускорения выполнения запросов созданы два индекса:

- idx_appointments_patient_datetime — индекс по идентификатору пациента и дате приёма;
- idx_appointments_doctor_datetime — индекс по идентификатору врача и дате приёма.

Индексы позволяют ускорить поиск записей на приём по пациентам и врачам с учётом даты.
